# 设计说明：从 Apple Podcasts 到自托管 Android 客户端

本文说明产品与架构取舍：参考了哪些成熟方案、哪些直接采用、哪些刻意不采用。

## 1. 参考对象

| 方案 | 类型 | 借鉴点 | 本项目取舍 |
| --- | --- | --- | --- |
| **Apple Podcasts** | 商业客户端 | 三 Tab 信息架构（资料库/发现/搜索）、节目页「订阅 + 单集倒序」、底部常驻迷你播放器、倍速与跳转、跨设备续播 | 采用同等信息架构；去掉需要 Apple 账号的云同步，改为自建账号 |
| **AntennaPod**（开源 Android） | 本地优先客户端 | RSS 解析模型（它用 Rome 解析 feeds）、订阅/队列/收藏三态、离线下载 | 采用其数据模型（订阅、待播、收藏、进度）；本项目把状态放服务端以便多设备 |
| **gPodder / gpodder.net**（开源同步协议） | 同步服务 | 订阅与单集的轻量同步 API 设计（`/subscriptions/{user}/{device}.json`、`/api/2/episodes/{user}.json`） | 不实现整套 gPodder 协议，但保留「按设备拉取快照 + 批量推送变更」的同步思路 |
| **Nextcloud gPodder Sync**（开源插件） | 自托管同步后端 | 证明「自建同步后端 + 多客户端」可行，SQLite/PG 单机足够 | 本项目同类定位，但用 Go 单二进制 + SQLite，降低运维成本 |
| **Podcast Index**（开放目录 API） | 目录服务 | 可替换目录的数据模型 | 默认不接入外部目录；不同协议需实现适配器，不能只换 URL |
| **Castopod**（开源播客托管） | 自建发布端 | 自建 RSS 生成 + 统计 | 不是本项目范围（我们做收听端） |

## 2. 信息架构（对齐 Apple Podcasts）

```
底部导航
├── 资料库   ← 「继续收听」+ 我的订阅 + 收藏 + 待播
├── RSS 导入 ← 粘贴有权使用的 RSS
├── 电台     ← 自行导入 / 大陆官方入口（浏览器外链）
└── 设置     ← 账号、服务器、播放偏好、改密码、退出

全局迷你播放器（常驻底部）→ 展开为全屏播放器（封面、标题、进度、倍速、跳转）
```

关键差异（自托管场景）：

1. **服务器地址可运行时切换**：App 不绑定单一后端，方便从测试环境切到正式域名，也便于自建用户。
2. **注册即账号**：不依赖第三方登录；首个注册用户自动成为 `admin`，方便自建实例初始化。
3. **导入优先**：默认不聚合全球播客或电台。外部目录配置为空时不发网络请求；管理员启用兼容目录前应确认授权与大陆地区适用性。
4. **官方来源与授权分开**：只提供云听、央广网的官网入口，不抓取隐藏直播地址，不绕过付费、DRM 或地区限制；详见 [内容来源说明](<CONTENT_SOURCES.md>)。

## 3. 数据模型

服务端 9 张表（SQLite，WAL）：

```
users ──┬── refresh_tokens（旋转、可撤销、按设备）
        ├── subscriptions ── podcasts ── episodes
        ├── progress（position_ms / duration_ms / completed）
        ├── episode_actions（starred / queued / downloaded）
        ├── playlists ── playlist_items
        ├── devices（last_seen_at）
        └── user_settings（倍速、跳转秒数、下载策略、主题）
```

设计要点：

- **软删除 + UPSERT**：订阅/进度/收藏都带 `deleted` 标记与 `UNIQUE(user_id, x)`，
  这样「取消订阅」也能作为一次可同步的变更，而不是让另一台设备误以为数据丢失。
- **单集以 (podcast_id, guid) 唯一**：RSS 抓取可反复执行而不会重复入库。
- **进度以毫秒存储**：客户端 ExoPlayer 的 position 直接映射，避免秒级取整导致续播抖动。
- **播放列表与队列分离**：`episode_actions.queued` 是临时待播；`playlists` 是长期清单。

## 4. 认证与安全

- **密码**：Argon2id（m=64MB, t=3, p=2），历史 bcrypt 哈希在校验成功后自动升级。
- **访问令牌**：JWT HS256，默认 15 分钟；刷新令牌是 32 字节随机串，**只存 SHA-256**，默认 30 天。
- **旋转与重放拦截**：刷新时立刻撤销旧令牌，重复使用旧刷新令牌会失败（测试覆盖）。
- **改密踢出**：修改密码后撤销该用户全部刷新令牌。
- **未知字段拒绝**：请求体 `DisallowUnknownFields` + 2MB 限制，降低脏数据与放大攻击面。
- **传输**：生产由 Caddy 终止 TLS 并附加 HSTS；客户端允许 http 仅为方便自建调试
  （`network_security_config.xml` 已标注该取舍）。

## 5. 同步策略

移动端弱网/切后台频繁，采用「**快照拉取 + 增量推送**」而非 CRDT：

```
POST /api/v1/sync
  body: { items: [ {episodeId, positionMs, durationMs, completed, playedAt, starred?, queued?} ] }
  resp: { subscriptions, progress, actions, playlists, settings, serverTime }
```

- 推送只带「本机发生的进度与标记变更」，服务端 UPSERT；
- 返回完整快照便于客户端做「服务端为准」的对齐；
- `serverTime` 可作为下次同步的游标（当前实现返回全量，数据量小、实现简单；
  多设备重度使用时再引入 `updated_at > ?` 增量）。

为什么不直接上 CRDT/双向 diff：单人/小团队的播客收听状态冲突极少，语义上「最后写入位置」即可，
引入 CRDT 会让服务端与客户端都复杂一个数量级。

## 6. 音频与播放

- **不托管或转播音频**：客户端直连用户导入的地址，后端保存元数据与使用状态。直连并不免除版权或公开运营的合规义务。
- **Media3 + ExoPlayer + MediaSessionService**：后台播放、通知栏、锁屏、耳机按键全部由框架处理。
- **进度回传**：播放中每 5 秒、暂停/拖动时各回传一次；进入某集时先读服务端进度再 seek（>3s 且未听完才跳）。
- **倍速与跳转**：存在服务端 `user_settings`，换设备保持一致。

## 7. 与「纯本地」开源客户端的差异

AntennaPod 这类本地优先方案的优势是**完全离线可用**、无服务端成本；
本项目选择服务端优先，换来：

| 维度 | 本地优先（AntennaPod） | 本项目（自建后端） |
| --- | --- | --- |
| 多设备一致性 | 依赖额外同步服务 | 原生支持 |
| 账号与权限 | 无 | 邮箱注册、邀请码、角色 |
| 运维成本 | 0 | 一台小云主机 + 一个容器 |
| 隐私 | 全本地 | 数据在你自己的服务器，可审计 |
| 离线 | 强 | 需后续补下载模块（服务端已留 `downloaded` 标记） |

## 8. 刻意未做的部分

- **音频转码/托管**：不碰版权内容。
- **社交与评论**：需要内容审核与合规，单机实例收益低。
- **RSS 定时抓取**：当前是「按需抓取 + 手动刷新」，避免在没有后台任务队列时引入定时器复杂度；
  后续可用 `time.Ticker` 或外部 cron 调用 `POST /podcasts/{id}/refresh`。
- **对象存储**：封面直接引用播客原图 URL，不落盘。
